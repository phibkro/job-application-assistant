## Bounded hydration default (L4): 5 per run, **provisional**

`INGESTION_HYDRATION_PER_RUN`, an Effect `Config` (`Config.schema(Int, 0..40) + withDefault(5)`) read from the
Worker env through `ConfigProvider.fromUnknown` in `decodeEnv`; malformed values fail as `EnvironmentIncomplete`.
Basis (`apps/worker/src/ingestion/hydrationBudget.ts`):

- The lazy driver's run reads one feed page (`maxPages: 1`) of at most `FEED_PAGE_SIZE = 5` entries; 5 keeps pace with
  what one run can add.
- **Measured** in `store.live.test.ts` against the scripted NAV: a run with N = 5 over a 6-ACTIVE + 1-INACTIVE page
  made exactly 1 feed request + 5 detail requests (the INACTIVE one is not a candidate); the next run made 1 more and
  then none were left; with no allowance (WS-0020's budgets) the request list is exactly WS-0020 T1's (feed root +
  tail). Production adds at most 1 public-token request and 2 `SourceLease` Durable Object calls: ≤ 9 per run, under
  the 50-per-invocation limit `design-specs/deferred-hydration.md` designs against. Each fetch is also bounded by the
  run's remaining 25 s.
- **Not measured: live NAV latency, rate limits or staging subrequest counts.** The real default is set from the
  first staging measurement (L4); NAV-Q9 carries the label.

## Decisions and deviations for the reviewer

1. **Hydration allowance lives in the run budget.** `RunBudget.maxDetailFetches` absent means 0 (an allowance not
   granted). The lazy driver grants the `Config` value; WS-0020's and `ingestion/live.test.ts`'s explicit budgets
   grant none, which is why their NAV request lists are unchanged. `lazy.test.ts`'s `toEqual(DEFAULT_RUN_BUDGET)`
   holds because `DEFAULT_RUN_BUDGET.maxDetailFetches` is the same provisional 5.
2. **Background hydration writes only the observation store and the projection**, not `canonical_jobs`. `getJob`
   (and its on-open `Hydration` service) is unchanged, so WS-0020 T5/G2 (read-path fetch) stand as before. The
   on-demand `Hydration` service was not converted to the decide loop (doing so would change a route's code path);
   the bounded-hydration lifecycle is the run's `HydrateDetails(n)` command.
3. **Projection membership is today's identity** (`occurrences.canonicalJobId`, D05). Merged requisitions fuse;
   `store.live.test.ts` pins Heltid + 50 % in one merged vacancy as Conflicting. TB-02 replaces the input.
4. Column names follow the repository's camelCase (`workloadMin`, `workloadMax`, `workloadState`), not the
   contract's `workload_min` spelling.
5. The workload filter filters the scanned page after the fact: a page may hold fewer than `limit` jobs; `nextCursor`
   still follows the scan. Invalid `workloadMin`/`workloadMax` die like an unrecognised `status` (the endpoint
   declares no 400).
6. Test edits to existing files, none weakening an assertion: `nav/src/index.test.ts` (2 assertions extended with
   the new `observation` field), `db/Sqlite.test.ts` (3 new tables in the pinned list), `runtime/Env.test.ts` (new
   cases), `scripts/test_d1_migrations.py` (0006), `testSupport/applySchema.ts` (splits on line-ending `;` so a
   one-line trigger stays whole), the three accounts tests (`Layer.provideMerge`, which **retires EFX-002/003/004**
   as their registry entries said WS-0022 would).
7. Known limits: free-text percentage parsing can misread unrelated percentages ("100 % fornøyde kunder"); the
   hydration-candidate query and `Projection.rebuild` scan all observations of a source / write one D1 batch, fine
   at fixture scale, to be chunked before the corpus is large; a defect (not a typed failure) in a detail fetch ends
   the run after its page commit, with the lease released (`releaseOnAbort`), as defects did before.
8. `quirks.test.ts` imports `apps/worker/src/ingestion/hydrationBudget.ts` to tie NAV-Q9 to the configured default (a
   test-only cross-package import).
